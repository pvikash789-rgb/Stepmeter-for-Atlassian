Which problem should the Atlassian build solve?

Status: decided. Vikash picked option 1, the automation step-cost optimizer (D-12). Kept below for the record.

Round 2 shortlist (D-11). Every idea below passed the shipped check and the data-access check. Ranked on usefulness and viability only (D-08).

1 · Automation step-cost optimizer Ranked 1st

Reads every automation rule, estimates the steps each one burns per month under the new metered pricing, ranks the expensive ones and shows how to rewrite them to cost less.

Metered billing starts 3 Dec 2026 for nearly every cloud org, overage is on by default, and Enterprise loses unlimited automation. Atlassian's native view is per meter and app, not per rule. Risk: rule data needs an admin API token, so it ships as a web tool, not a Forge app. Verify API access on day 1.

2 · "I'm affected too" for the JSM portal Close 2nd

Agents mark a ticket as a known issue. Portal customers see it and click "I'm affected too" instead of filing a duplicate, and get every update. Agents see how many customers are hit.

JSDCLOUD-1743 has 491 votes and has been open since 2015. No Cloud app does it. Forge portal modules can run for customers, so it's fully buildable and Marketplace-shippable. Risk: Atlassian marks it "Reviewing".

3 · Idea-to-delivery sync for Product Discovery

Keeps each Product Discovery idea's status in step with its linked epics and flags mismatches.

Clear gap, but evidence is community threads, not votes, and Forge write access to ideas needs a spike.

4 · Broken-link checker for Confluence

Finds dead page, Jira and smart links across a space.

108 votes, very buildable, but an established app already has 572 installs.

Considered and set aside this round: expiring "Verified" pages and approval reminders (crowded with new apps getting 1 to 4 installs), sprint carryover tracking (crowded), CSAT insights and long-term SLA history (Atlassian signalling it will build them), MCP usage dashboard and leaver handoff (thin demand), anything on Teamwork Graph (early access only). Round 1 options A to E are below for the record.

Round 1 (closed)

E · Knowledge gap finder Dropped, already shipped

Reads resolved tickets, groups recurring questions that no help-center article answers, and drafts the missing article from how agents actually resolved them, for a human to approve.

Any JSM team with a help center has this pain, not just Premium. AI deflection depends on article coverage. Data comes from standard Jira and Confluence APIs. Value is countable: tickets a month that could be self-served. Must verify Atlassian doesn't already ship this.

A · Triage accuracy monitor 2nd

Compares Service Triage suggestions with what agents finally set, by request type and over time.

Useful, but only for teams on Premium or Enterprise using Service Triage. Unclear whether the agent's original suggestion is recoverable from ticket history.

C · Eval harness for Forge agents 3rd

Offline test runner for Rovo agents built as Forge apps.

Fully buildable, real gap. Small audience of Marketplace developers.

B · Agent governance roll-up Thesis only

One admin view of every Rovo agent's evals, usage and inactivity.

Strongest demand signal, but no public API exposes agent data today, so it can't be built as a real product. Use it as a written thesis instead.

D · Scope boundary tester Dropped

Probes agents with out-of-scope questions.

There's no supported way to call a Rovo agent from backend code, so automated probing isn't viable.

D-078 Oct
DecidedAtlassianFrom research

Don't build a plain ticket-triage agent for Atlassian

Why
Jira Service Management already ships a Service Triage Rovo agent that suggests request type, urgency and priority, and flags escalations. Rebuilding it would look like we hadn't done our homework.
Instead
Move to the layer around agents: measuring whether they are right, and giving admins visibility and control. Rovo has per-agent evaluation (CSV datasets up to 100 prompts) and conversation review, but public feature requests ask for an org-wide compliance view and richer audit logs, and admins say they can't trace which sources an agent queried.

D-108 Oct
DecidedAtlassianFrom research

Drop the knowledge gap finder: Atlassian already ships it

Why
Since April 2026, Rovo in Jira Service Management has a manage-knowledge-base skill that finds high-impact topics with no documentation and drafts Confluence articles from resolved tickets for review. Rovo Chat can also compare a ticket's resolution with an existing article and update it.
Lesson

D-118 Oct
DecidedMethodAtlassian

Scout widely, then gate every idea on three checks

What we did
Four parallel research tracks: Jira and Product Discovery, Confluence and Loom, Jira Service Management, and Rovo plus admin. About 20 ideas reviewed.
Gates
Demand evidence (votes, threads, paid apps). Not already shipped by Atlassian. Data reachable through a public API or Forge module. Ideas failing any gate were dropped before ranking.
Learned
New single-purpose Forge apps on the Marketplace often get only 1 to 4 installs, so distribution is the hard part. Prefer pain that is urgent or long-ignored over pain that many apps already chase.
D-128 Oct
DecidedAtlassianBuild

Build the automation step-cost optimizer

Why
Metered billing starts 3 Dec 2026 and touches nearly every cloud org. Atlassian shows usage per meter and app, not which rules cost the most or how to fix them. Value is measured in money saved.
Key facts
The rule management API returns each rule's full configuration with an admin API token (no OAuth or Forge), so it ships as a web tool. The API also returns secrets in clear text, so the tool must redact them and never store rule data. There is no public API for how often each rule runs, so run frequency must be estimated or entered by the admin.
Plan
Phase 0 validation spike (days 1 to 3) with kill criteria, then the cost engine, then recommendations and report, then a beta with 5 to 10 real admins, then launch and outreach before 3 Dec.
Kill if
The API can't be called as expected, or most admins interviewed say they already know which rules are expensive.
D-138 Oct
DecidedDistribution

Build in public on GitHub from day one

Why
A public repository gives a timestamped history of the work week by week, which is stronger proof than a finished project that appears all at once. GitHub Pages serves the build journal and this log as a site that is easy to share with recruiters.
Guardrails
Tokens live only in a local .env file. Rule data from any real site, even redacted, stays in a git-ignored folder. The spike script was tested offline to confirm it strips URLs, headers and tokens.

Things to verify before building

  • Whether Atlassian already offers knowledge-gap detection for help centers, through the virtual service agent, Rovo Service or elsewhere. One article found no such report, and an open request says the virtual agent doesn't learn from interactions, but this needs a hands-on check.
  • Getting Rovo on a developer site. One community report says Rovo agents weren't enabled for a site registered with a personal Gmail address. Check trial options or a work-email sign-up early.
  • Whether the built-in evaluation flow works for Forge-built agents. A developer thread says it's unclear; Atlassian folks have pointed to offline evals instead.
  • Role level. Recent JSM Cloud PM roles in Bengaluru asked for 3 to 5+ years of product experience, so frame the 32 months plus this build carefully.
