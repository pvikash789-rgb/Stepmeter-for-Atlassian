Stepmeter for Atlassian

An automation cost tool that tells Atlassian Cloud admins which automation rules will cost the most under metered billing, and how to rewrite them to cost less.

Started 8 Oct 2026 Billing change 3 Dec 2026 Current phase 0 · Validation

The problem

From 3 December 2026, Atlassian bills automation per step. Every trigger, condition, action, branch and loop in a rule run counts as one step, even when the trigger finds nothing to do. Steps come from a pooled monthly allowance, overage costs $0.50 per 1,000 steps and is switched on by default, and Enterprise plans lose unlimited automation. If an admin turns overage off, rules stop when the allowance runs out and missed events are not replayed.

Admins can see usage per meter and per app, with forecasts and caps. What they can't easily see is which of their hundreds of rules are expensive and how to fix them. One daily rule that branches over 500 issues can burn more steps than fifty simple rules together.

What the tool does

Connect a site, and it reads every automation rule, estimates each rule's monthly step cost, ranks the worst ones in money terms, and suggests specific cheaper rewrites. Rule data is processed without being stored, and secrets inside rules are stripped.

How I'm approaching the build

  • Validate before building. A three-day spike with written kill criteria comes first. If the rule API doesn't give what we need, or admins already know their expensive rules, I switch to the backup idea.
  • Be honest about estimates. No public API reports how often each rule runs, so run frequency is estimated. I'll measure the estimate against Atlassian's real usage figure and publish the error.
  • Treat security as a feature. The rule API returns webhook URLs and credentials in plain text. The tool strips them and never stores rule data.
  • Real users before launch. 5 to 10 admins run it on their own sites before any public post.
  • How I work. I use an AI assistant (Claude) for research and coding. Problem choice, product decisions and trade-offs are mine, and each one is recorded with its reasoning in a decision log.

Journal

8 Oct 2026 · Day 0, evening

Phase 0 kit ready, building in public

Decided to build in a public GitHub repository so the history of the work is visible as it happens.

Wrote the Phase 0 kit: 17 test automation rules, each designed to exercise one pattern that changes step cost (noisy triggers, conditions placed last, branches over sub-tasks and searches, hourly schedules), a spike script that lists and reads every rule, and an interview guide for Jira admins.

The rule API returns secrets in plain text, so the script strips URLs, headers and tokens before saving anything. Tested it offline against a fake rule with four planted secrets: all four were removed and the component counts came out right.

8 Oct 2026 · Day 0

From a vague plan to one problem

Started with a rough idea: research products at Atlassian, ServiceNow and Salesforce, build something, and share it with people there. Narrowed it to proof-of-work over critique, and Atlassian first.

Spent the day on discovery. Three early ideas died on research: two were already shipped and one had no data access. Ran a wider scout of about 20 ideas with strict gates, verified the shortlist's key facts, and chose the automation step-cost optimizer.

Before building, confirmed two things that shape the design. The rule API works with an admin API token, which means a web tool instead of a Marketplace app. It also returns secrets in plain text, which makes redaction a core requirement.
